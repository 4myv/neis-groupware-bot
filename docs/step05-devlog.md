# 5단계 개발 기록: 예외 처리

## 이 문서를 다 읽으면 할 수 있게 되는 것

1. NEIS나 Slack이 실패했을 때 프로그램이 무엇을 하는지 순서대로 설명할 수 있다.
2. 관리자 채널의 오류 알림과 `logs/bot.log`를 보고 원인을 찾을 수 있다.
3. 5단계에서 실제로 겪은 문제와, 로그에서 비밀값을 지키는 방법을 알 수 있다.

## 1. 목표

CLAUDE.md 예외 처리 표 중 이번 단계에서 다룰 것:

| 상황 | 처리 | 결과 |
| --- | --- | --- |
| 급식이 없는 날 | 정상 상황으로 보고 안내 문구를 보냄 | 3단계에서 완료. 이번에 `INFO-200`을 "쓸 수 있는 응답"으로 명시 |
| NEIS API 응답 없음·오류 | 잠시 후 한 번 재시도, 그래도 실패하면 관리자에게 오류 알림 | **이번 단계** |
| Access Token 만료 | 새 토큰을 발급받아 요청을 다시 보냄 | **이번 단계** |
| 서명이 맞지 않는 콜백 | 요청을 거부하고 로그에 기록 | 7단계 |
| 콜백 중복 수신 | 응답을 바로 돌려주고, 같은 메시지는 한 번만 처리 | 6~7단계 |

그리고 다음 두 가지도 이번 단계에서 한다.
- 오류 알림: "API 호출이나 전송이 실패하면 관리자에게 알림"
- 로그: "모든 요청과 오류는 시각과 함께 로그 파일에 남긴다."

3단계에서 남긴 한계("NEIS 오류도 '급식이 없습니다'로 보임")도 고친다.

## 2. 한 일 (순서대로)

1. **로그 설정**: `app/log.py`를 만들었다. `logs/bot.log`에 "시각 [등급] 내용"으로 남긴다.
2. **NEIS 예외 처리** (`app/neis.py`)
   - 결과 코드가 `INFO-000`(정상)이나 `INFO-200`(데이터 없음)이 아니면 실패로 본다.
   - 요청 실패, JSON이 아닌 응답, 예상과 다른 모양도 실패로 본다.
   - 실패하면 3초 뒤 한 번 재시도하고, 그래도 실패하면 `NeisError`를 일으킨다.
3. **Slack 예외 처리** (`app/auth.py`, `app/sender.py`)
   - 재발급 코드를 `refresh_and_save`로 분리하고, 재발급이 실패하면 `SlackAuthError`를 일으키게 했다.
   - `post_message`는 `token_expired`나 `invalid_auth`가 오면 새 토큰으로 한 번 다시 보낸다.
   - 어떤 실패에도 오류를 일으키지 않고 `{"ok": ..., "error": ...}`를 돌려준다.
4. **알림 흐름** (`app/notifier.py`)
   - 급식 알림 한 번(조회 → 변환 → 전송)을 `send_lunch_notification`으로 묶었다.
   - 실패하면 관리자 채널(`SLACK_ADMIN_CHANNEL_ID`)로 알린다.
5. **스크립트와 테스트**: `send_lunch_message.py`가 `send_lunch_notification`을 쓰게 바꿨다. 테스트 9개(`test_neis.py` 5개, `test_sender.py` 4개)를 추가했다.
6. **실제 상황 시험 A~E**: 개발자의 Slack으로 메시지 3개가 갔다. (4번)
   - 급식 알림 채널: 정상 알림 1개
   - 관리자 채널: 시험 B의 오류 알림 1개, 시험 D의 `[시험]` 메시지 1개
7. **비밀값 검사**: requests 오류 메시지에 인증키가 들어 있는 것을 확인했다. 로그 파일에 비밀값이 없는 것도 확인했다. (5번 문제 1)
8. **개발자 질문 반영**: 개발자가 시험 B의 오류 알림을 보고 이유를 물었다. 알림에 원인이 없어서 생긴 일이라, 원인이 알림까지 전달되도록 `app/neis.py`를 고쳤다. (5번 문제 2)
9. 학습 정리와 개발 기록을 쓰고, 비밀 파일이 커밋 대상에 없는지 확인한 뒤 커밋한다.

## 5. 발생한 문제와 해결

### 문제 1. requests 오류 메시지에 인증키가 들어 있음

- **상황**: 처음에는 오류 메시지를 로그에 그대로 쓰려고 했다. 그 전에 연결 실패 오류의 메시지를 검사했다(메시지 자체는 출력하지 않고 포함 여부만 확인).
- **원인**: requests는 오류 메시지에 요청 주소 전체를 넣는다. NEIS 요청 주소에는 `KEY=인증키`가 붙어 있다. 검사 결과는 `True`였다.
- **해결**
  - 외부 요청 오류는 **종류 이름**(`type(error).__name__`, 예: `ConnectionError`)만 로그와 알림에 쓴다.
  - `except` 안에서 새 오류를 일으킬 때 `from None`을 붙였다. 처리되지 않아 화면에 나와도 원래 오류(인증키가 든 메시지)가 함께 보이지 않는다.
  - 로그 파일 전체를 검사해 비밀값이 없는 것을 확인했다. (결과 5)

### 문제 2. 오류 알림에 원인이 없어서 개발자가 이유를 물어봄

- **상황**
  - 시험 B의 오류 알림을 본 개발자가 "급식 불러오기 실패한 이유가 뭐야?"라고 물었다.
  - 그때 알림에는 "원인은 logs/bot.log에 있습니다"라고만 적혀 있었다.
- **원인 (두 가지)**
  1. 처음 구조에서는 `try_neis_once`가 실패하면 빈 딕셔너리(`{}`)를 돌려줬다. 그래서 원인(`ERROR-290` 등)이 로그에만 남고 알림까지 전달되지 않았다.
  2. 에이전트가 시험 전에 "관리자 채널로 알림이 간다"고는 알렸지만, 알림 자체에는 시험이라는 표시가 없었다.
- **해결**
  - `try_neis_once`가 실패하면 **원인을 담은 `NeisError`를 일으키게** 바꿨다.
    - NEIS 결과 코드가 원인이면 코드와 NEIS의 공식 설명을 담는다. (예: `ERROR-290 인증키가 유효하지 않습니다...`)
    - 요청 자체가 실패했으면 `응답을 받지 못함(ConnectionError)`처럼 종류 이름만 담는다.
  - `call_neis_api`는 그 오류를 잡아 재시도하고, 두 번째에도 실패하면 원인을 붙여 다시 일으킨다. 알림에 원인이 바로 보인다. (결과 4)
  - 결과 코드를 꺼내는 함수를 `get_result_code`(코드만)에서 `get_result`(코드와 설명)로 바꾸고 테스트도 고쳤다.
  - 고친 뒤 확인할 때는 관리자 채널로 다시 보내지 않고, 보낼 문구를 화면에만 출력했다.
- **이 질문과 답은 학습 정리 6번에 넣었다.**

## 6. 결정한 것과 이유

| 결정 | 다른 선택지 | 고른 이유 |
| --- | --- | --- |
| `INFO-000`, `INFO-200`만 쓸 수 있는 응답으로 봄 | `ERROR-`로 시작하는 것만 실패로 보기 | 명세에는 `INFO-300`(관리자에 의해 인증키 사용 제한) 같은 실패도 `INFO-`로 시작한다. 쓸 수 있는 것을 명시하는 편이 안전하다. |
| 재시도는 한 번, 3초 뒤 | 여러 번, 점점 길게 기다리기 | CLAUDE.md 규칙이 "잠시 후 한 번 재시도"다. |
| 결과 코드 오류(예: `ERROR-290`)도 똑같이 한 번 재시도 | 오류 종류에 따라 재시도 여부를 다르게 | 인증키 오류는 재시도해도 소용없지만 3초 늦어질 뿐이다. 규칙을 하나로 두는 편이 이해하기 쉽다. |
| NEIS 실패는 `NeisError`를 **일으킴** | 빈 딕셔너리 돌려주기 (처음 구조) | 원인을 알림까지 전달할 수 있다. 실패하면 메시지를 만들 수 없으니 부르는 쪽이 반드시 처리하게 한다. (문제 2) |
| Slack 전송(`post_message`)은 실패해도 **일으키지 않고** `ok: False`를 돌려줌 | `SlackError`를 일으키기 | Slack 응답이 원래 `ok`/`error` 모양이다. 연결 실패·토큰 문제도 같은 모양으로 맞추면, 부르는 쪽은 `ok`만 보면 된다. |
| 토큰 오류로 보는 코드는 `token_expired`, `invalid_auth` 두 개 | `token_expired`만 | 시험 D처럼 토큰이 맞지 않을 때도 `invalid_auth`가 왔다(4단계 결과 5). 새 토큰으로 한 번 더 해 볼 가치가 있다. |
| 관리자 알림은 관리자 전용 채널로 | 관리자 1:1 메시지 | 4단계에서 정한 대로 추가 권한이 필요 없다. |

## 7. 다음 단계에서 할 일 (6단계: 콜백 서버)

1. FastAPI와 Uvicorn을 설치하고, Slack이 보내는 요청을 받는 콜백 엔드포인트를 만든다. 받은 메시지는 출력한다.
2. Slack 공식 문서에서 Events API의 요청 모양, URL 확인(`url_verification`) 절차, 응답 시간 제한을 확인한다.
3. Slack 앱 설정에 필요한 것을 정리한다. 이벤트 구독, Request URL, 메시지를 읽는 권한(scope)이 필요하다. 권한을 추가하면 앱을 다시 설치해야 할 수 있다. 이번에는 토큰 자동 교체가 켜져 있어서, 다시 설치할 때 토큰이 어떻게 되는지도 공식 문서로 먼저 확인한다.
4. **개발자의 역할**: Slack 앱 설정 변경, 터널 도구 실행.
   - 터널 도구(ngrok, Cloudflare Tunnel)는 가입 나이 조건을 먼저 확인한다. (개발자는 미성년자)

## 이번 단계 핵심 정리

1. NEIS가 실패하면 3초 뒤 한 번 재시도하고, 그래도 실패하면 원인을 담은 `NeisError`로 관리자 채널에 알린다.
2. Slack 토큰 오류(`token_expired`, `invalid_auth`)면 새 토큰을 받아 한 번 다시 보낸다.
3. `post_message`는 어떤 실패에도 `{"ok": False, "error": ...}`를 돌려준다.
4. 모든 요청과 오류는 `logs/bot.log`에 시각과 함께 남는다.
5. requests 오류 메시지에는 인증키가 섞여 있어서, 종류 이름만 남기고 `from None`으로 원래 오류를 숨긴다.
